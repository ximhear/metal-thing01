# 사용자 관점 앱 평가

개발자가 아니라 **처음 앱을 받은 사용자**의 눈으로 앱을 쓴다. 코드를 읽고 추측한 평가와 실제로 실행해서 본 평가를 반드시 구분한다.

## 1. 준비

- 기획서(`docs/plan/`)가 있으면 읽고 핵심 사용자 스토리를 평가 과제로 쓴다. 없으면 앱을 보고 핵심 과제 3~5개를 정한다.
- 페르소나 1~2개를 정한다(예: "Metal을 모르는 일반 사용자", "그래픽에 관심 많은 창작자"). 평가 내내 그 사람처럼 생각한다.

## 2. 빌드와 실행

- 빌드: `xcodebuild -list`로 scheme 확인 → `xcodebuild -scheme <S> -configuration Debug -derivedDataPath build build`.
- macOS 앱: `open build/Build/Products/Debug/<App>.app`, 화면은 `screencapture -x <경로>.png`.
- iOS 앱: `xcrun simctl boot <기기>` → `xcrun simctl install booted <App>.app` → `xcrun simctl launch booted <bundle id>` → `xcrun simctl io booted screenshot <경로>.png`. 다크 모드는 `xcrun simctl ui booted appearance dark`.
- 클릭·입력이 필요하면 computer-use 스킬(사용 가능할 때)로 직접 조작한다.
- 스크린샷은 `docs/reviews/<날짜>/` 아래에 저장하고 직접 열어 본다.
- 빌드나 실행이 안 되면 그 자체가 가장 심각한 발견이다. 에러 출력을 그대로 기록하고, 실행하지 못한 항목은 "확인 못 함"으로 표시한다. 지어내지 않는다.

## 3. 평가 항목

각 핵심 과제를 실제로 해 보면서 기록한다: 무엇을 하려 했나 → 무엇을 눌렀나 → 무엇이 일어났나 → 기대와 달랐던 점.

| 항목 | 보는 것 |
|---|---|
| 첫인상 (5초) | 이 앱이 뭘 하는지 바로 알 수 있나, 첫 행동이 분명한가 |
| 과제 완료 | 핵심 과제를 도움 없이 끝낼 수 있나, 몇 단계 걸리나 |
| 사용성 | 피드백(눌렀을 때 반응), 되돌리기, 일관성, 에러 메시지, 빈·로딩 상태 |
| 시각 완성도 | 정렬, 여백, 타이포, 색, 다크 모드, 창 크기 변화 |
| 성능 | 실행 시간, 버벅임, 애니메이션·렌더링 부드러움(가능하면 fps나 Instruments 수치), 발열·CPU |
| 접근성 | Dynamic Type, VoiceOver 레이블, 대비, 키보드 조작(macOS) |
| 플랫폼다움 | Apple HIG에 맞는가, macOS면 메뉴·단축키·창 동작 |

## 4. 리포트

`docs/reviews/<YYYY-MM-DD>-review.md`로 저장한다.

```markdown
# <앱 이름> 사용자 평가 — <날짜>

## 요약
한 문단: 사용자로서 전체 인상, 가장 좋았던 점 1개, 가장 큰 문제 1개.

## 평가 환경
빌드 결과, 기기/OS, 페르소나, 실제로 실행했는지 여부.

## 점수 (각 5점)
| 항목 | 점수 | 근거 |
총점과 한 줄 평.

## 과제별 기록
### 과제 1: …
- 결과: 성공 / 어려움 / 실패
- 관찰:
- 스크린샷:

## 발견한 문제 (심각도 순)
| # | 심각도 | 문제 | 사용자에게 미치는 영향 | 제안 |
심각도: 치명(과제 불가) / 높음(헤맴) / 중간(불편) / 낮음(다듬기)

## 좋았던 점

## 다음에 고칠 것 Top 3
```

## 원칙

- 칭찬과 문제를 모두 구체적으로 쓴다. "UI가 별로다"가 아니라 "설정 버튼이 아이콘만 있어 무엇인지 알 수 없다".
- 근거가 실행 관찰인지, 코드만 보고 짐작한 것인지 표시한다.
- 개선 제안은 작게 바로 고칠 수 있는 것부터. 고치는 작업은 `swiftui-expert` / `metal-expert` 스킬로 넘긴다.
