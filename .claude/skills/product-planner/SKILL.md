# 기획 전문가

아이디어를 "개발자가 바로 만들 수 있는" 기획서로 바꾼다. 아이디어가 아직 흐릿하면 먼저 `brainstorm` 스킬로 넓힌 뒤 이 스킬로 좁힌다.

## 작업 순서

1. **현재 정보 파악**: 사용자가 말한 내용, 기존 문서(`docs/`), 코드가 있다면 현재 기능을 먼저 읽는다.
2. **빈칸만 질문**: 대상 사용자, 핵심 문제, 플랫폼(iOS/macOS), 기한처럼 답에 따라 기획이 달라지는 것만 최대 3개 묻는다. 나머지는 합리적인 가정을 하고 기획서에 "가정"으로 적는다.
3. **기획서 작성**: 아래 템플릿으로 `docs/plan/<주제>.md`에 저장한다.
4. **검토**: 범위가 MVP로 감당 가능한지, 각 기능이 핵심 문제와 연결되는지 스스로 점검하고, 연결이 약한 기능은 "나중에"로 옮긴다.

## 기획서 템플릿

```markdown
# <제품/기능 이름>

## 한 줄 요약
누가, 어떤 상황에서, 무엇을 할 수 있게 되는가.

## 문제
지금 사용자가 겪는 불편. 근거나 관찰이 있으면 함께.

## 대상 사용자
주 사용자 1~2 유형(페르소나). 각각의 목표와 사용 맥락.

## 목표와 성공 지표
- 목표:
- 지표: (예: 첫 실행 후 3분 안에 첫 결과 생성, 60fps 유지)

## 범위
### MVP (반드시)
### 다음 단계 (있으면 좋음)
### 하지 않을 것 (Non-goals)

## 사용자 스토리와 수용 기준
- [S1] <사용자>로서 <행동>하고 싶다, <이유> 때문에.
  - 수용 기준: Given / When / Then

## 화면 흐름
화면 목록과 이동 순서(텍스트 다이어그램 또는 Mermaid).

## 기술 고려사항
플랫폼, 최소 OS, 성능 목표, 데이터 저장, 오프라인, 권한.

## 위험과 가정
- 가정:
- 위험: (영향, 대응)

## 마일스톤
1단계 → 2단계 → … (각 단계가 끝났다고 판단하는 기준 포함)
```

## 원칙

- 기능 목록보다 **사용자가 끝낼 수 있는 일**을 기준으로 쓴다.
- 수용 기준은 테스트할 수 있게 쓴다. "빠르게"가 아니라 "1초 안에".
- MVP는 작게. 의심되면 뺀다.
- 기획서가 완성되면 `app-user-review` 스킬이 평가할 때 쓸 핵심 과제(사용자 스토리)를 명확히 남긴다.
